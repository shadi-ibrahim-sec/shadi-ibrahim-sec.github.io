E-Commerce Web
Application Assessment.

Black-Box Pentest · June 2026 · Authorized
E-Commerce Web Application
redacted-client-app.vercel.app  ·  Next.js / Supabase
✓ Written Authorization Obtained
2 Critical Findings
2 Med / Low Findings
4 Controls Verified
Findings — click any item to toggle details

The order-creation endpoint POST /api/orders accepted price and total directly from the client JSON body without server-side re-validation. By intercepting the checkout request in Burp Suite and modifying "price": 79.99 to "price": 2, a 201 Created response was returned — confirming an order at an arbitrary price.

⚡ Impact: Any authenticated user can purchase any item for $0.01. Because the platform uses Cash on Delivery with no third-party payment gateway, there is no downstream re-validation, creating uncapped financial risk.

Navigating directly to /admin/orders while authenticated as a standard "role":"User" account rendered the full admin panel with zero server-side role enforcement. Every customer's full name, phone number, delivery address, and order history was immediately accessible.

⚡ Impact: Mass PII exposure for all registered customers due to missing server-side authorization checks. Classified Critical under OWASP A01:2025.

Consecutive failed login attempts against the same account returned identical, immediate "Invalid login credentials" responses with no lockout, progressive delay, or CAPTCHA challenge triggered.

⚡ Impact: Exposes user accounts with weak or previously breached passwords to automated credential-stuffing and brute-force attacks.

Submitting "price": -10 caused an unhandled server exception returning HTTP 500 with an empty body — confirming the absence of numeric boundary validation on the order endpoint.

⚡ Impact: Unhandled server exception indicating broader schema and numeric boundary validation gaps.

Four controls were actively tested and confirmed secure: Stored XSS — React's output encoding rendered payloads safely. CSRF — SameSite=Lax cookie policy blocks cross-origin POST requests. Admin Write Authorization — order status updates properly returned 403 Forbidden for standard users. IDOR — cross-account direct order ID lookups returned 404 Not Found.

✓ Verified baseline controls documented so engineering teams preserve them during remediation.

Bug Bounty · AI Platform

Race Condition in
AI Session Timer.

Responsible Disclosure · July 2026 · Authorized
AI Gateway — Session Timer Bypass (TOCTOU)
[REDACTED] · AI Coding-Assistant Platform
✓ Vendor Triaged · High Severity · Bounty Awarded
1 High Severity Finding
2 Independent Reproductions
1 Vendor Confirmed
Findings — click any item to toggle details

The daily-usage session check on the AI gateway endpoint POST /v1/messages was enforced only at request intake. By dispatching a long-running AI completion (large max_tokens) and calling POST /api/launch/session/stop within ~0.5–1.6s, the in-flight generation continued executing and returned a full response 9–20 seconds after the session was confirmed closed server-side.

⚡ Impact: Enables unbilled AI compute consumption after session timer termination, directly matching the vendor's published High-severity scope definition. Tested strictly on the researcher's own account with zero impact on other users.

Configured Burp Suite's Turbo Intruder with dual RequestEngine instances (one targeting the AI gateway, one targeting session control) synchronized via a shared gate. Confirmed reliability across two independent test sessions.

⚡ Key Insight: Demonstrates that long-running streaming/AI endpoints require continuous quota validation or active stream cancellation upon session closure rather than intake-only checks.

Submitted through the vendor's official security channel and confirmed within days: "You are correct that an in-flight AI request can continue after the usage session timer is stopped... We are classifying this as High severity according to our published bug bounty category."

✓ Issue validated, classified High severity, and rewarded with 3 months of complimentary platform access.

Cloud PaaS & Container
Platform Assessment.

Grey-Box Security & API Review · November 2026 · Authorized VDP
Cloud PaaS & Container Deployment Platform
*.[target-paas].dev  ·  Spring Boot / Mobile & MCP API
✓ Responsible Disclosure · Case Study
1 Low / Info Finding

Findings & Verified Controls — click any item to toggle details

The login endpoint POST /login returned distinct error responses depending on whether the submitted email address existed in the system: "No account found with this email address" vs. "Incorrect password". Notably, /forgot-password properly returned a unified generic message.

⚡ Impact: Differentiable error strings allow automated verification of registered email addresses, aiding credential-stuffing or targeted phishing. Reported privately under responsible disclosure with a recommendation to unify authentication error responses.

Extracted mobile/MCP API routes via static source analysis of the official Model Context Protocol (MCP) connector package and tested cross-account access across 8 endpoints (GET/POST/PUT /api/mobile/containers/{id}, /logs, /env, /deployments/{deploymentId}). Control tests on owned resources confirmed genuine persistence-layer ownership checks.

✓ All unauthorized cross-tenant requests were strictly rejected with 404 Not Found or 403 Forbidden.

Verified immediate session invalidation upon logout, instant legacy API key revocation upon regeneration, cross-surface token isolation (X-API-Key rejected on /web/api/**), strict scope enforcement (read < deploy < manage), and backend allow-listing against mass assignment on profile updates.

✓ Strong defense-in-depth architecture across authentication, scope boundaries, and input sanitization.

Business Logic & Access Control · SaaS

Energy Procurement
Platform Assessment.

Grey-Box Business-Logic & API Review · November 2026 · Authorized VDP
Energy & Renewable Procurement Platform
*.[target-energy].org  ·  Multi-Tenant B2B Web Application
✓ Responsible Disclosure · Case Study
1 Low / Info Finding
4 Multi-Tenant Entities Tested
4 Core Controls Verified
Findings & Verified Controls — click any item to toggle details

The endpoint GET /api/company/{company_id}/pending-invoice-items — designed to generate production invoice numbers and pending payout objects for onboarded Producer accounts — returned 200 OK for an unpaid Corporate company (subscription_status: "checkout_started"). While company ownership was strictly validated, account tier and payment state were not enforced.

⚡ Impact: Limited practical impact on fresh test accounts (zeroed payout values), but represents a defense-in-depth state-validation gap if historical Corporate accounts enter an unpaid or downgraded state. Recommended enforcing explicit Producer-role and active-subscription checks server-side.

Tested cross-account access across billing, invoice, and projection endpoints using two independent accounts owning multiple Corporate and Producer companies. Notably, passing mixed owned and unowned IDs in array parameters (?company_ids=owned&company_ids=unowned) accurately isolated and rejected the exact unauthorized ID with 404 Not Found.

✓ Object-level ownership is consistently enforced even on batch/array query parameters.

Identified internal administrative endpoints (/api/admin/money/ledger/companies/{id}) via compiled frontend JS bundle inspection and verified that standard user tokens receive an ambiguous 404 Not Found (resisting endpoint enumeration). Also confirmed server-side allow-listing against injecting "payment_required": false during corporate onboarding.

✓ Backend RBAC, anti-enumeration error handling, and onboarding payment enforcement are properly implemented.
